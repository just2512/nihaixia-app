# 全局 AI 能力审计与改造执行约束

> **文件性质：项目执行约束 / 验收标准。** 本文件约束后续全局 AI 审计、实现、测试和真机验收。与既有业务代码冲突时，不得擅自扩大 AI 权限；先记录冲突、说明影响，再按本文安全边界处理。
>
> 生效基线：`master` @ `2c3cf60b8d7b02286f733e364fbff94f03e1da46`（2026-11-10）。此 SHA 是本文件制定时的审计基线，不代表后续实现状态。

## 1. 目标与问题定义

目标不是“接入 Agent”或重建一套 AI 架构，而是让五种模式在真实场景中形成可追踪、可验证、受约束的任务闭环：

`用户输入 → 安全检查 → 意图/实体理解 → 检索与上下文组装 → 模型决策/解释 → 参数校验 → 业务执行 → 结果核对 → 结果展示与跨轮延续`

**首要交付是失败分类证据，不是功能清单或架构图。** 每个失败场景必须归入以下类别之一；若证据不足，标 UNKNOWN，不得猜测：

| 类别 | 判定 | 优先排查位置 |
|---|---|---|
| 理解失败 | 意图、复合子目标、指代或实体识别错误 | Orchestrator、实体解析、槽位提取 |
| 检索失败 | 应召回的资料未命中、命中错误或排序遗漏 | Repository、索引、别名与检索策略 |
| 上下文失败 | 已召回资料未正确注入、被错误截断/压缩或来源丢失 | Prompt/Context Builder、长度预算、历史拼装 |
| 执行失败 | 工具未调用、参数错误、业务执行失败、结果未回传或被忽略 | ToolRouter、能力适配层、业务函数、结果协议 |
| 模型能力上限 | 输入、检索、上下文、工具结果均正确，模型仍无法完成受限任务 | 任务缩小、分步、模板化或接受模型边界 |

不得将上述类别混为“AI 不聪明”。不得在失败分类尚无场景证据时，以建设统一核心、Agent、DAG 或更换模型作为默认修复。

## 2. 架构约束：复用现有系统，不另起炉灶

### 2.1 八层仅作对照检查表

用户交互、安全、知识业务、状态记忆等层优先核实现有代码对应物。每层必须记录“现有文件/函数、实际调用方、测试证据、缺口”，不得将八层直接拆成八个新模块或八项重构工程。

重点验证的缺口是：
1. 意图理解到复合任务与缺参澄清；
2. 页面入口背后的业务函数能否脱离 Widget/BuildContext 独立调用；
3. 多个可信业务结果能否按来源约束综合解释并展示。

### 2.2 明确禁止的重复建设

未经审计证明必要且获得项目决策确认，不得：
- 重建 AIWorkbench、五种模式、Orchestrator、ToolRouter 或会话/消息数据库表；
- 新建通用 Agent 平台、DAG 工作流引擎或复杂任务图；
- 以“统一架构”为由把现有规则问诊、知识库和业务算法迁移到模型；
- 先引入向量数据库、Embedding、LangChain、云端模型/API 或原生 Function Calling；
- 把学习测验、批改、复习计划等新产品功能混入 AI 核心改造。此类功能需独立立项，明确是否新增学习状态存储。

实现优先采用小型线性任务计划；若确有多步需求，先使用最多 5 步的顺序计划和显式引用，不引入 DAG。不得为了架构整齐而复制已有状态或业务逻辑。

## 3. 端侧 E4B 的职责分工与预算

必须遵守“代码确定性、模型语义性、代码执行与验证”的边界：

| 环节 | 责任方 | 允许职责 |
|---|---|---|
| 红旗与安全门禁 | Dart/原生确定性代码 | 输入检查、急症红旗、领域权限、拒绝条件；不得只依赖 system prompt |
| 初步路由 L0 | Dart | 稳定规则、模式约束、缩小候选域 |
| 候选工具筛选 | Dart + E4B | 代码将候选缩小到最多 5–6 项；模型在受约束结构中选择或请求澄清 |
| 实体解析与槽位 | 代码优先，模型辅助 | 输出候选实体/槽位；ID、类型、必填项由代码核验 |
| 检索与上下文 | Dart | 明确来源、条数、字符/token 预算、截断状态及失败状态 |
| 业务执行 | Dart 业务函数 | 参数校验、确定性计算、权限检查、错误处理 |
| 结果核对 | Dart | 校验返回类型、完整性、单位、来源和执行状态 |
| 综合解释 | E4B | 仅根据已验证结果组织语言；区分事实、规则、App 数据和 AI 归纳 |

不要求每轮都调用模型做规划。简单单意图请求可走确定性路径；复杂或歧义请求才进入模型辅助选择/槽位提取。结构化输出必须有 schema、解析失败处理和重试上限，不得把自由文本 JSON 当作可信参数。

**预算要求：**
- 每次模型调用记录模型/后端、轮次、输入字符数、可取得时的 token 数、输出字符数、耗时和异常。
- 不得把字符数冒充 token 数；token 统计能力不存在时写 UNKNOWN。
- Prompt/context 必须分段记录来源与预算；超限应按条目边界和优先级裁剪，并显式标记哪些来源被省略。禁止无提示地从任意字符位置截断而仍声称上下文完整。
- 上下文预算以 Find N2 实测可稳定运行的值确定，不从其他手机的公开性能数据推算。

## 4. 三种领域硬边界

### 4.1 玄学大师

- 排盘、起卦、历法、干支与数值计算必须调用 App 确定性业务逻辑；模型不得心算伪造计算结果。
- 必要输入缺失（例如出生时辰、日期、地点或起卦条件）时必须追问；不得静默补默认值、推测时辰或替用户选择算法。
- 输出明确分区：**计算结果**（App 业务函数返回）与**文化性解读**（AI 归纳），并标注采用的输入和算法。
- 玄学请求不得调用问诊、诊断、处方或剂量能力。

### 4.2 问诊助手

- 辨证结论只允许来自现有 DiagnosticEngine/DiagnosticRules；方剂与药物资料只允许来自 App 已有可信数据。
- 模型可整理用户自述、抽取候选症状、指出缺失信息和提出澄清问题；不得独立诊断、生成证型、开方、加减或计算个体剂量。
- 自由文本抽取结果必须保留原始用户表述并标为待确认；未经用户确认不得写入规则问诊答案。
- 胸痛、呼吸困难、意识障碍、突发偏瘫/言语障碍、大量出血、自伤风险等红旗必须在模型调用和普通问诊路由前由确定性逻辑拦截；不得仅依赖模型遵守提示词。

### 4.3 综合层与来源

每条实质性结论必须可区分以下来源类型：
- `原文`：可定位的原始资料；
- `规则结果`：DiagnosticEngine 或其他确定性规则引擎结果；
- `App 数据`：本地数据库、计算器或业务函数返回；
- `AI 归纳`：模型对已提供信息的解释或综合。

不得把 AI 归纳伪装成原文、规则结果或 App 计算值。资料缺失、来源定位未核验、字段为空或检索失败时，必须明确写缺失；不得补造书名、版本、条文号、出处、参数或结果。来源引用必须能回链到实际 source ID/业务结果。

## 5. 证据标准与状态定义

每条审计结论必须附证据类型和定位：

- `CODE`：文件路径、函数/类名、行号或稳定代码定位；
- `TEST`：测试文件、测试名称、断言覆盖的输入与输出；
- `TRACE`：真实设备/运行环境的 trace ID、场景编号、关键日志片段和设备/版本信息。

证据优先级不是互相替代关系：CODE 证明实现路径存在；TEST 证明自动化条件下行为；TRACE 证明指定设备和场景真实运行。测试通过不能替代真机 TRACE，静态代码不能替代运行结果。

能力状态统一为：
- `IMPLEMENTED`：CODE + 对应 TEST + Find N2 真机完整 TRACE 均通过，且无未解释断点；
- `PARTIAL`：至少有可验证实现，但调用链某一环未通过、未覆盖或证据不完整；必须写明断点；
- `MISSING`：已检查目标调用链，确认不存在该能力；
- `UNKNOWN`：没有足够证据判断，或设备/日志/源码不可得。

禁止仅凭注册表项、页面入口、提示词、测试文件存在或模型回复通顺标记 IMPLEMENTED。无法取得 Find N2 时，相关项目保持 UNKNOWN/PARTIAL，不得推定通过。

## 6. 动态 TRACE 规范

### 6.1 必须覆盖的节点

每个场景以同一 `trace_id` 关联以下节点；不适用的节点显式记录 `NOT_APPLICABLE`，不能静默缺失：

`input → redflag → route(L0/L1/L2) → entity_resolution → retrieval → context_assembly → model_input/output → tool_parse → argument_validation → business_execution/result → result_validation → final_render → persisted_state`

至少记录：
- 场景编号、trace_id、时间戳、App commit/version、设备型号、Android 版本、模型文件版本、实际 GPU/CPU backend；
- 路由层级、命中规则/候选工具、实体 ID/类型/解析状态；
- 检索 query、命中/未命中条数、source ID、来源状态、被裁剪条目；
- 注入模型的各段来源、字符数、可用 token 数、截断标记；测试环境可保存完整 prompt，真机默认不保存敏感正文；
- 模型原始输出的结构化解析状态、耗时、异常类型；工具参数校验结果、业务函数签名/执行结果状态；
- 最终展示内容与来源引用的一致性、会话持久化和跨轮状态恢复结果。

### 6.2 隐私与日志安全

- TRACE 默认关闭；通过显式 Debug/审计开关启用，不得默认向正式用户持续记录对话正文。
- 健康症状、出生信息、图片、音频、个人身份信息不得写入普通持久化日志。默认只记录脱敏摘要、长度、字段状态和不可逆关联 ID。
- 如测试确需保留原文，必须由测试人员明确授权，限定本地受控环境、用途和保留期限；不得上传公共 CI 日志或仓库。
- 不记录模型文件、密钥、数据库内容或完整个人会话快照。
- TRACE 关闭时不得改变业务结果、执行顺序或安全门禁；日志写入失败不得阻断用户业务。

### 6.3 运行判定

一条场景 TRACE 必须能从输入关联到最终展示；关键节点缺失即不能判定完整通过。业务调用状态要区分 `NOT_STARTED`、`SUCCEEDED`、`FAILED`、`UNKNOWN`；执行结果未知时禁止自动重放有副作用的操作。

## 8. 每个场景的记录模板与失败分类统计

每个场景一份记录，字段至少包括：

| 字段 | 内容 |
|---|---|
| Scenario / trace_id | 场景 ID 与唯一关联 ID |
| Environment | Find N2 型号、系统、App SHA/version、模型修订、backend |
| Input | 脱敏输入摘要；原文仅在授权本地测试记录 |
| Expected | 预期路由、实体、工具、参数、来源和安全结果 |
| Observed trace | 按第 6 节节点记录实际结果 |
| Verdict | PASS / FAIL / BLOCKED / UNKNOWN |
| Failure class | 理解 / 检索 / 上下文 / 执行 / 模型上限 / 安全阻断 / UNKNOWN |
| Evidence | CODE / TEST / TRACE 定位 |
| Latency | 总耗时及可取得的阶段耗时 |
| Follow-up | 最小修复项、回归测试和复测场景 |

失败分类统计必须按场景统计，给出分子/分母和 UNKNOWN 数量；一个场景可记录多个断点，但主失败原因必须说明判定依据。不得用未经执行的场景、模型主观评价或代码推断填充统计表。

## 9. 执行阶段与交付物

### P0：多轮稳定性与安全门禁（并行启动）

1. 核查并修复 E4B 第二轮及后续 `state:7`、空回复、GPU/CPU fallback、Conversation 重建与 transcript 恢复。
2. 恢复 Conversation 时必须恢复一致的必要历史上下文；若无法安全恢复，明确停止并要求用户显式重试。
3. 区分请求未执行、执行状态未知、执行成功但响应丢失；未知状态禁止盲目重放。
4. 红旗检查必须在模型调用之前确定性执行，并有负向测试。
5. 增加对应 Kotlin/Flutter 自动化回归；Find N2 连续多轮实测单独验收。

### P1：静态调用链与失败基线审计（不改业务行为）

交付 `docs/ai-capability-audit.md`，至少包含：
- 五种模式的提示词、工具、检索源、模型调用与结构化输出；
- 输入到最终展示的逐跳文件/函数调用链；
- ToolRouter 每个工具的页面入口/独立业务函数分类及函数签名；带 `BuildContext` 的入口不算 Headless；
- Prompt 注入内容、字符/token 预算、截断策略；
- 实体名称到 ID 的解析、别名表与缺口；
- 现有业务能力尚未向 AI 暴露的清单；
- 每项结论 CODE/TEST/TRACE 证据，缺证据标 UNKNOWN；
- 初始失败分类统计仅统计实际执行场景，未执行场景单列 UNKNOWN。

### P2：审计 TRACE 能力

- 增加默认关闭的审计日志开关和 trace_id 贯穿机制；
- 覆盖第 6 节关键节点，完成脱敏和日志隔离测试；
- 证明关闭 TRACE 时业务行为不变，打开时日志可关联完整调用链；
- 不允许为审计改造顺手重写业务路由或提示词。

### P3：Find N2 场景集实测与失败归因

- 按第 7 节逐项执行；设备不可用的场景标 UNKNOWN，不得以模拟测试替代真机结果。
- 每个失败记录断点、失败分类、证据和复测结果。
- 形成按真实失败数量排序的分类分布；先修主因类别，再扩展能力。

### P4：按证据最小化修复

- 检索失败：先修查询拆分、实体/别名映射、召回与排序，不先建 Agent。
- 上下文失败：修预算、分段、来源完整性、跨轮实体与引用传递。
- 理解失败：在 L0 确定性筛选后，用 E4B 做受约束选择/槽位填充和缺参澄清。
- 执行失败：抽取最小 Headless 业务函数适配器，要求无 Widget/BuildContext 依赖，定义 typed args/result、校验、错误与取消语义。
- 模型上限：缩小任务、拆成线性步骤、给出模板或明确限制；不得以编造结果掩盖上限。

### P5：统一结果协议与综合解释

仅在前述失败证据支持时实施。结果至少包含：能力 ID、输入参数、执行状态、结构化数据、单位、source IDs、来源类型、缺失字段、错误状态。AI 只能基于通过校验的结果解释；最终展示保留来源和不确定项。

## 10. 考核目标与放行门槛

| 目标 | PASS 条件 | 未通过处理 |
|---|---|---|
| 失败分类 | 所有已执行场景均有失败类别或 PASS；未执行项单列 UNKNOWN；统计可复算 | 不得进入架构扩建 |
| 调用链可观测 | 每条已验收 TRACE 从输入关联到最终展示；关键节点无静默断链 | 标 PARTIAL，先补 trace |
| 红旗安全 | 所有红旗负向测试在模型调用前命中；不存在仅靠 prompt 的保护 | 阻断发布 |
| 领域隔离 | 问诊与玄学负向用例不能跨域调用；规则结果不能被模型覆盖 | 阻断相关能力上线 |
| 工具执行 | 参数校验、业务执行、结果验证、最终展示可追溯；未知状态不盲目重放 | 标 PARTIAL，禁止声称闭环 |
| 来源可信 | 原文/规则/App 数据/AI 归纳清楚区分；缺失不补造 | 阻断相关来源型回答 |
| 跨轮一致性 | X-01/X-02/X-03 通过；会话不串线；恢复结果可核验 | P0 未关闭 |
| 自动化质量 | 新增逻辑有针对性单测/集成测试；相关 CI 全绿 | 不得合并为完成 |
| 真机验收 | Find N2 目标场景有实际 TRACE，设备、模型、版本、backend 记录完整 | 未实测项保持 UNKNOWN |
| 架构范围 | 每个新增抽象均能指向已证实失败；无重复会话表、DAG 或通用 Agent 平台 | 撤回无证据的扩建 |

**发布硬门槛：** 红旗前置拦截、问诊/玄学领域隔离、工具执行状态安全、来源不编造、跨轮会话隔离必须 PASS。任何一项 UNKNOWN 都不能宣称相关能力已完成；任何一项 FAIL 都阻断相关能力发布。

## 11. 改进排序规则

审计完成后输出前 10 项改进清单，按“用户影响 × 改动成本”进行定性排序，不使用虚构分数、权重或成功率。每项必须列：
- 真实失败场景与失败类别；
- 影响用户任务及复现条件；
- 最小修改范围和依赖；
- 风险/回滚方式；
- 对应测试与 TRACE 复测；
- 完成定义。

优先处理安全阻断、数据/会话错乱、真实高频断点；不得因为某项容易实现就绕过更严重的失败。

## 12. 执行纪律

1. 先审计和采证，再依据失败分类决定改造；不得先写大规模架构再寻找问题。
2. 每次提交说明改动文件、对应场景、失败类别、测试和 CI 证据。
3. 静态代码、自动化测试、模拟设备、真机 TRACE 分开报告，不得相互冒充。
4. 不得删除或弱化现有安全校验、规则引擎、来源状态和用户确认流程来追求“AI 自动化”。
5. 对未知行为明确标 UNKNOWN；不以推测补齐报告。
6. 本文件是约束性基准。若需修改范围、硬边界或放行条件，必须在文档中记录理由、影响和决策依据，不能在实现中悄悄偏离。
