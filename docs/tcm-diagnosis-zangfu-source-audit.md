# 脏腑信号来源与问诊字段映射审计

> 审计对象：上游 `Wsy-prog/tcm-diagnosis-system/index.html` 的 `TEN_QUESTIONS`、`collectSignals()`、脏腑展示代码；App `master` 的 `DiagnosticRules.tenQuestions`、`DiagnosticEngine.answerTenQuestion()`、`answerFlatQuestion()`、`diagnoseByRules()`。
> 本文只审计代码中的数据来源与字段映射，不验证中医理论、诊断效度或临床适用性。

## 结论

**目前不能把上游脏腑标签直接映射到 App 的问诊选项，也不应据此直接开发自动脏腑分析。**

原因不是 App 缺少一个简单字段，而是两套问诊模型的题目、题序、选项和数据语义并不一致。上游的权重键还混合了脏腑、六经和其他概念；它的“脏腑倾向”不是纯脏腑数据，也不是独立诊断算法。

本轮不修改诊断引擎，不新增脏腑判断，不改变方剂和处方输出。

## 一、上游数据实际做了什么

上游 `collectSignals()`：

1. 遍历 `TEN_QUESTIONS`，按数组下标读取 `answers[i]`。
2. 未作答（`null`）直接跳过；选择正常项（`-1`）只写入正常备注。
3. 其他选项加入异常列表，并读取选项对象的 `meridians` 映射。
4. 键属于六经时累加到 `meridianScore`；其他所有键一律累加到 `zangfuScore`。
5. 报告页将 `zangfuScore` 排序并显示“脏腑倾向分析”。

这里有两个重要事实：

- `zangfuScore` 并非只含脏腑：上游选项还使用 `血`、`气`、`阴虚` 等非脏腑键。将这些值全部放入同一对象，是上游实现的字段命名宽泛，不应在 App 中照搬。
- 上游在没有六经主证时，还会取最高的 `zangfuScore` 项作为 `primary` 兜底。随后该值会进入以六经为键的提示逻辑。这会把“信号标签”提升成“主证”，App 必须拒绝这种兜底路径。

## 二、上游脏腑标签的来源

上游 `TEN_QUESTIONS` 中明确出现的脏腑键及对应选项如下。权重数值只用于识别上游原始数据，不作为 App 的评分或展示内容。

| 上游标签 | 触发选项（上游原文标签） | 备注 |
|---|---|---|
| 肝 | 1–3 点醒来；胸胁苦满/胁痛 | 两个不同问项 |
| 肺 | 3–5 点醒来 | 仅一个选项 |
| 心 | 失眠整夜难睡；脚冰/足冷 | 两个不同问项 |
| 脾 | 没胃口；清谷不化；白天疲惫 | 三个不同问项 |
| 肾 | 小便清白次数多；起床困难/但欲寐 | 两个不同问项 |
| 血 | 固定不移刺痛 | 非脏腑键 |
| 气 | 胀痛 | 非脏腑键 |
| 阴虚 | 手足心热 | 非脏腑键 |

这些只是上游开发者写入选项对象的标签，不等于已经完成经典来源核验，也不代表这些选项对相关脏腑具有排他性或充分性。

## 三、App 与上游问诊模型不兼容

App 的十问结构当前为：

| App key | 问项 |
|---|---|
| temperature | 寒热 |
| pulse | 脉象 |
| thirst | 渴饮 |
| sweating | 汗出 |
| pain | 疼痛 |
| stool | 大便 |
| urine | 小便 |
| appetite | 胃口 |
| sleep | 睡眠 |
| energy | 精神 |
| menstrual | 月经/性功能 |
| vomit_type | 条件触发的呕吐类型追问 |

上游结构则为：睡眠、胃口、大便、小便、口渴、寒热、体力、汗、疼痛、足温。

两者存在以下不兼容：

1. **题序完全不同。** 上游用 `answers[i]` 绑定题目数组下标；App 用稳定的字符串 key 和 1-based 选项号记录答案。禁止按数组下标迁移。
2. **题目拆分不同。** App 把寒热、脉象、渴饮、汗出分成独立题；上游把脉舌放在进阶问诊，足温则是独立基础题。App 没有与上游“足温”完全等价的独立问题。
3. **选项颗粒度不同。** App 的睡眠、疼痛、尿液等选项与上游不是同一套枚举；同一自然语言描述也不保证语义相同。
4. **App 有额外题目。** 月经/性功能与条件触发的呕吐追问在上游十问中没有直接对应字段。
5. **正常、否定、未知必须区分。** App 有“没有此症状”、可跳过脉象和可缺失的扩展症状；不能把缺失当成阴性，也不能把未选脏腑信号当成反向证据。

因此，任何映射都必须以 App 的 `key + optionIndex + canonical option text` 为入口，不得复用上游的数组下标。

## 五、App 下一步允许的实施方案

在经典来源、选项语义和反证规则核验完成之前，不开发“脏腑辨证”或自动脏腑结论。

若后续要做辅助展示，只允许采用以下最小结构：

- **输入来源：** App 当前会话的 `qAnswers`、`extSymptoms` 和原始选项文本。
- **证据记录：** 问项 key、选项号、原始选项文本、来源文件/条目 ID。
- **状态：** 已选中 / 正常项 / 未作答 / 不适用；不作“反向证据”推断。
- **标签：** 只有经过独立来源核验的映射才可展示；未经核验的只显示原始问答，不标注脏腑。
- **呈现：** “相关问答线索”而不是“脏腑诊断/脏腑倾向”；不排序、不汇总分值、不生成主证。
- **安全边界：** 不推荐方剂、不输出剂量、不覆盖六经辨证、不让 E4B 裁决。

## 六、代码改动硬门禁

- 不改 `RuleEngine.evaluate()`、`RuleEngine.top()`、`coRecommended()`。
- 不改 `DiagnosticEngine.diagnoseByRules()` 的主结果。
- 不将脏腑信号用于合病判断或方剂筛选。
- 不把未知/未作答映射为阴性。
- 不把“血/气/阴虚”归为脏腑。
- 不迁移上游的累计权重、主证兜底和 70% 合病阈值。
- 新增展示必须配正常项、未作答、相似选项、否定语义、重复回答和矛盾回答测试。

### 本轮核验结论

1. **上游代码证据 PASS：** 可以确认这些标签确实写在对应选项的 `meridians` 对象中，且 `collectSignals()` 将六经之外的键全部汇入 `zangfuScore`。
2. **经典出处证据 MISSING：** 上游没有为上述标签提供逐条经典引用；顶部的知识库来源概述不能替代具体出处。
3. **临床有效性 UNKNOWN：** 即使某个概念能在经典中找到相近表述，也不能据此证明“某一现代问项选项 → 某脏腑标签”的映射有效，更不能证明其具有排他性。
4. **迁移结论 REJECT：** 不将这些标签迁入 App 的诊断、排序、主证、合病或方剂流程。后续如取得原始知识库文件，必须逐条补充原文、篇名、版本/卷次及语义解释，再独立评估映射；不能只补一个书名就视为通过。


## 九、2026-11-04：只读脏腑证据层已实施

当前 App 已建立独立的 `ZangFuEvidenceAssessment` / `ZangFuEvidenceRecord` 数据结构，并由 `ZangFuEvidenceBuilder` 从以下输入生成原始证据记录：

- App 稳定问项 key、1-based 选项号和 canonical 选项文本；
- 已回答的跟进问题，包括误下史、反复泻下史、心下痞硬、食积线索；
- 用户在问诊开始阶段主动选择的症状；
- 舌苔、舌形、主脉、兼脉；
- 扩展症状 key。

每条记录保留 `questionKey`、`questionLabel`、`optionIndex`、`answerText`、`state` 和 `sourceId`。状态区分已回答、明确正常、未知、未作答和非法选项。未作答/未知不转换为阴性。

展示层仍将 `organMappingStatus` 固定为 `MISSING`，`unclassifiedAdditionalEvidence` 只保留未分类扩展线索；没有脏腑映射、排序、分值、主证兜底、自动诊断、方剂或剂量输出。该层只负责展示“用户提供了哪些信息、来自哪个问项”，不参与六经、合病或方剂计算。

测试覆盖：
- 正常、未知、未作答、非法选项的状态区分；
- 舌象、主脉、兼脉独立记录；
- 跟进问答和用户选择症状的来源保留；
- 未知脏腑映射保持 `MISSING`。

**阶段状态：** 独立只读证据层已实现；脏腑标签/经典映射仍为 `MISSING`，不得把本次数据展示解释为脏腑辨证已经完成。
