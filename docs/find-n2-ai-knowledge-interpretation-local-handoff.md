# Find N2：AI 知识解读与键盘避让本地验收交接单

> **当前状态：LOCAL ONLY / NOT RUN。** 本文是针对 P0 知识解读、知识上下文传递和 P1 情境输入框键盘避让的设备执行单，不是 PASS 报告。所有设备结果必须由真实 OPPO Find N2 产生；CI、Widget test、模拟 viewInsets 和静态代码检查不能替代实机证据。

## 1. 本次交接范围

本地只执行此前尚未完成的两组验收，不重新实现代码，也不把无关 AI 工作扩进本任务。

| ID | 验收对象 | 必须确认的结果 |
|---|---|---|
| P1-IME | 外屏/内屏情境 AI 面板键盘避让 | 键盘出现后 composer 和 App 发送按钮始终可见；文字不丢；收起后恢复；折叠/展开不破坏布局 |
| P0-AUTO | 七类知识详情一键解读 | 点击后自动提交一次短意图；不要求编辑长提示；不把完整资料放进用户消息 |
| P0-CONTEXT | 后台知识上下文与跨轮追问 | 每轮仍绑定当前详情条目；无 source/anchor/version 串线；上下文失效时 fail-closed |
| P0-QUALITY | E4B 知识理解质量 | 不复述详情页；分析关系和内在逻辑；区分原文记载、归纳、MISSING/UNKNOWN；不补造内容 |

本单不覆盖：
- GPU/CPU 通用稳定性 20 轮、多媒体、Activity/进程恢复、AI 数据清理等既有专项。它们继续按总交接清单执行，不因本单完成而自动关闭。
- 经典阅读页选中文段后的自由提问。它不属于七类“当前知识详情条目”一键解读入口。
- 易经、八字、紫微、子午流注、节气、运气、剂量换算等确定性 `toolResult/fieldValue` 结果解释。它们使用独立结果快照/resolver，不得套用知识条目 adapter，也不得让模型重新计算。

## 5. P1：键盘避让实机验收

### 5.1 外屏 bottom-sheet：IME-OUT

1. 将 Find N2 合拢，打开 App。
2. 进入任一已迁移的知识详情，例如方剂详情，点击“问 AI 解读”。
3. 等待情境 AI bottom-sheet 出现。初始打开时不应因为自动解读而抢焦点或主动弹出键盘。
4. 点击 composer 输入框，确认系统键盘弹出。
5. 输入一段可辨认的测试文本：`外屏键盘可见性测试 123`。
6. 检查输入框完整位于键盘上方；光标和正在输入文字可见；App 自己的发送按钮完整可见且可点击。不要把系统键盘上的 Enter/发送键当成 App 发送按钮。
7. 在键盘保持打开时检查底部安全区、手势导航区和面板边界，没有重叠或裁剪。
8. 使用 App 发送按钮发送；确认消息进入当前会话，没有丢字或重复发送。记录发送后键盘是保持还是收起，不将某一种未约定行为自行当作 PASS 条件。
9. 使用系统返回键收起键盘。检查 composer、发送按钮和面板恢复到正常布局；输入框文本/会话状态没有异常。
10. 再次点输入框，重复一次输入和收起，排除仅首次打开正常。

**PASS**
- 键盘弹出后 composer 与 App 发送按钮均完全位于 IME 顶边之上。
- 文本输入、光标显示、发送均正常，无遮挡、跳动、裁剪、丢字或重复发送。
- 键盘收起后面板恢复，不残留额外空白或错误位移。

### 5.2 展开内屏 side-panel：IME-IN

1. 展开 Find N2，确认应用窗口稳定后进入同一类知识详情。
2. 点击“问 AI 解读”，确认助手以内屏 side-panel 显示。
3. 点击 composer，弹出系统键盘，输入：`内屏键盘可见性测试 456`。
4. 检查 composer 和 App 发送按钮完全位于键盘上方；文字与光标可见；面板没有被 Dialog inset 与内部布局重复压缩。
5. 使用 App 发送按钮发送，再通过系统返回键收起键盘；确认 side-panel 恢复正常高度、宽度和位置。
6. 在键盘收起状态下关闭面板、重新打开，再测试一次，排除 route 残留旧 inset。

**PASS**
- 内屏 side-panel 正常显示，输入框和发送按钮不被键盘覆盖。
- 已输入文本保留，发送成功，收起后窗口尺寸/位置恢复。
- 没有双重避让造成的过度缩小、顶部/底部大片空白或面板不可滚动。

### 5.3 折叠状态切换：IME-FOLD

分别执行：
- 内屏打开助手并弹出键盘时，合拢设备；检查转为外屏后当前会话、输入文本和输入框状态。
- 外屏打开助手并弹出键盘时，展开设备；检查转为内屏后 side-panel/route 的位置及输入状态。
- 对系统实际支持的半折叠姿态进行同样检查；记录设备是否能在键盘保持可见时完成姿态切换。

**PASS**
- 姿态切换后没有崩溃、黑屏、错位、输入内容丢失或发送按钮被遮挡。
- 当前会话和未提交文本按实际路由生命周期保持；若系统主动收起键盘，必须记录系统行为，并确认 composer 仍可重新聚焦。
- 恢复到原姿态、收起键盘后布局正常。

**限制**
- 如果 ColorOS 在折叠切换时主动关闭键盘，可以记录为系统行为；不能把“键盘没有保持弹出”单独判为代码失败。但输入内容、会话和重新聚焦能力仍必须验证。

## 6. P0：七类入口自动启动与上下文绑定

### 6.1 七类入口逐个冒烟

至少在一个 Native 实际 backend 已确认的会话中，对以下入口各执行一次：

| 场景 ID | 入口 | 操作 |
|---|---|---|
| AUTO-FORMULA | 方剂 | 打开具体方剂详情，点击 AI 解读 |
| AUTO-HERB | 本草 | 打开具体本草详情，点击 AI 解读 |
| AUTO-ACUPOINT | 穴位 | 打开具体穴位详情，点击 AI 解读 |
| AUTO-ACUPUNCTURE | 针灸处方 | 打开具体处方条目，点击 AI 解读 |
| AUTO-CASE | 医案 | 打开具体医案详情，点击 AI 解读 |
| AUTO-MERIDIAN | 六经 | 打开具体六经详情，点击 AI 解读 |
| AUTO-NEIJING | 内经 | 打开具体条文详情，点击 AI 解读 |

每个入口检查：
1. 点击后无需再编辑或点击发送，模型就绪且情境会话初始化完成后自动启动一次分析。
2. 用户消息/对话记录是短意图，不出现完整 JSON、sourceId、anchorId、版本号、本地文件路径或内部约束文本。
3. 不自动弹出键盘或抢走输入焦点。
4. 分析内容对应当前打开的条目，不得串到上一个页面或上一次会话。
5. 不应重复启动两次。可通过消息时间线和脱敏 TRACE 的 request/turn 元数据核对。

**模型尚未加载的等待场景另测一次：**
- 在模型未加载时从一个知识详情点击解读。
- 应等待模型可用，不得提前发送、不应丢失 pending 意图。
- 模型加载完成、会话初始化完成后自动提交一次。
- 多次状态刷新、页面重建或等待过程不得重复提交。
- 若初始化失败或 contextRef 无效，应显示明确失败/UNKNOWN，不得拿旧缓存资料继续分析。

### 6.2 当前条目上下文和追问

选取一个方剂条目作为主场景；优先使用本地资料中实际存在且字段较完整的桂枝汤。如果该条目在当前数据集中不存在，选择一个实际可打开、组成字段完整的方剂，并在记录中写明真实条目名称，不得造测试数据。

操作：
1. 在详情页点击 AI 解读，等待第一轮回复。
2. 记录当前详情标题；确认回复讨论的是当前条目，而不是其它条目。
3. 发送追问：`你刚才分析的整体结构，分别依据当前条目中的哪些信息？请区分条目明确记载和你的归纳，不要重列完整组成。`
4. 再发送追问：`当前条目没有直接说明的配伍作用有哪些？请明确标记无法确认的部分，不要用常见说法补齐。`
5. 检查两轮追问仍然围绕原条目，前文指代有效；不能要求用户重新粘贴条目或再次编辑长提示词。
6. 返回详情页，重新打开另一个条目，再启动新解读；确认新会话绑定新条目，不继承上一条目的数据。
7. 如 App 提供本地来源/引用入口，点击并确认回到当前条目；无法打开或定位到另一条目时记 FAIL。

**PASS**
- 初次点击只启动一次；每轮追问继续使用同一个当前条目上下文。
- 切换到另一条目后上下文同步切换，没有跨条目串线。
- 内部 source/evidence ID 不作为普通回答文本暴露；App 本地来源回填指向正确条目。
- 锚点、版本或来源解析失败时 fail-closed，不使用缓存旧条目回答。

## 7. P0：E4B 解读质量验收

这部分必须记录 GPU 与 CPU 两组结果。两种 backend 分开建会话，不能把 GPU fallback 到 CPU 的回复算作 GPU 结果。

### 7.1 每个 backend 的前置操作

1. App「设置 → 本地 AI → E4B 推理后端」选择待测 backend。
2. 按 App 流程加载模型；确认 Native 返回的实际 backend。
3. 若选择 GPU 但实际返回 CPU，GPU 场景记 `BLOCKED` 或按真实故障记 `FAIL`，不得将该轮算作 GPU PASS；另外可在 CPU 组独立复测。
4. 新建独立对话，避免上一个 backend 或旧条目上下文污染本轮。
5. 记录模型状态、加载时间、实际 backend、会话 ID 的脱敏标识和每轮 trace_id。

### 7.2 代表性内容场景

对 GPU 和 CPU 各执行以下三种场景。每个场景都通过详情页的一键解读入口启动，不手工粘贴完整资料。

**A. 方剂组方关系（FORMULA-QUALITY）**
- 使用桂枝汤或本地资料中另一个组成字段完整的方剂。
- 初始分析应说明整体结构、条目实际标注的药物角色及配伍关系。
- 不得把详情页已有药物/剂量清单重新完整罗列。
- 追问：`请把你提出的关系逐项对应到当前条目的依据；哪些是明确记载，哪些是根据条目内容归纳？`
- 追问：`哪些问题当前条目无法确认？请保留 UNKNOWN，不要补充条目未提供的禁忌、剂量或临床证据。`

**B. 本草信息关系（HERB-QUALITY）**
- 选择本地存在、性味/归经/功用字段较完整的本草条目。
- 初始分析应解释这些字段之间能建立的关系，而不是逐项释义后结束。
- 追问：`你刚才的归纳分别由哪些条目字段支持？原文没有直接建立的关系请明确标出。`
- 追问：`当前条目没有提供哪些信息？不要根据模型记忆补齐。`

**C. 医案证据链（CASE-QUALITY）**
- 选择 App 内已有医案详情，不输入任何真实个人病例。
- 初始分析应尝试梳理该记录包含的症状、病机、治法、方药之间的对应关系。
- 只能解释该病例实际记录的内容；不能将单一医案泛化为普遍疗效或治疗规范。
- 追问：`把记录明载的内容和你根据记录作出的推断分开说明；每个推断指出依据。`
- 追问：`这份记录不能支持哪些结论？请明确列出未知，不要自行补齐。`

若某条目确实缺少上述字段，不得为通过验收而换成虚构内容；记录真实数据缺项，并检查模型是否正确说明不足。

### 7.3 输出验收断言

每个初始回答和追问分别检查：

| 断言 | PASS 条件 | FAIL 条件 |
|---|---|---|
| 不复述 | 不重新完整罗列详情页已有资料；仅引用解释关系所必需的少量内容 | 主要内容仍是逐字段改写或重抄完整列表 |
| 有分析 | 至少说明当前条目中两个或多个信息之间的关系/结构，且关系解释有当前资料依据 | 只有概述、释义、换词，没有关系分析 |
| 原文与归纳分开 | 明确标出条目明确记载与基于条目的归纳，并解释归纳依据 | 把模型推断伪装成原文事实 |
| 未知处理 | 对条目未提供的信息明确说明 MISSING/UNKNOWN 或“当前资料无法确认” | 用常识或模型记忆擅自填空 |
| 不编造 | 不新增条目未提供的组成、剂量、禁忌、出处、临床证据或规则 | 出现无法由当前条目支持的具体事实 |
| 连续追问 | 两次追问都保持当前条目和前文指代；不要求重新粘贴资料 | 追问失去条目、串到旧条目或重新要求长提示词 |
| 输出可用 | 回复非空、结构连贯、能回答用户实际问题 | 空回复、重复循环、乱码、无关输出或协议拒绝 |

**该项只有所有适用断言通过才可记 PASS。** 一次回答中出现编造的药物/剂量/出处或把归纳伪装成原文，整条场景记 FAIL，并保存最小复现与 trace_id。

若当前 TRACE 未记录某个本应出现的阶段或关联 ID，不能根据 UI 看起来正常就推定 PASS；该项记 UNKNOWN，并保留缺失阶段说明。TRACE 记录本身不得改变业务行为。

## 10. 状态判定与失败处理

| 状态 | 使用条件 |
|---|---|
| PASS | 在真实 Find N2 上执行，所有该场景断言满足，并保存可复核证据 |
| FAIL | 真实设备上观察到违反预期的行为，或出现可确认的错误结果 |
| BLOCKED | 硬件、签名、模型文件、backend 或环境前置条件缺失，无法开始有效测试 |
| UNKNOWN | 已开始测试，但关键状态/日志/实际 backend/上下文归属无法确认 |
| NOT RUN | 尚未执行 |

不要用百分制、主观打分或“感觉正常”替代以上结果状态。

失败归属建议：
- 输入框/发送按钮被键盘遮挡、键盘收起后位置异常：P1 IME。
- 一键点击未自动发送、重复发送、自动抢键盘焦点：P0 自动入口行为。
- 页面内容进入用户消息、source/anchor/version 串线、追问丢上下文：P0 上下文传递。
- 回复只复述、没有关系分析、来源归纳混淆、补造资料：P0 解读质量。
- 状态不明或 TRACE 断链：UNKNOWN，不允许推测为通过。

发现 FAIL 后，不要通过关闭测试、降低断言或删除失败记录修复。先保留证据，回到源码定位最小责任层；P0 语义、P0 上下文和 P1 IME 必须保持独立修复任务。修复后对相关失败场景复测，并确认没有破坏其它已通过场景。
