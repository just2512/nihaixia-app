### 下载与导入

1. 使用上方 Hugging Face 直链，将模型下载到电脑或手机本地存储；浏览器下载中断时，先确认文件完整再导入。
2. 电脑端可用 PowerShell 校验：`Get-FileHash .\\gemma-4-E4B-it.litertlm -Algorithm SHA256`；必须与上表完全一致。
3. 安装本项目 APK，进入「问诊」→ 右上角本地 AI →「选择并导入模型文件」，从系统文件选择器选择下载文件。
4. 应用会将文件复制到私有目录，先校验字节数和 SHA-256，再替换正式模型；导入失败不会把未校验文件交给推理引擎。
5. 显示“模型文件已安装”后点击「加载本地模型」。模型不会打包进 APK，也不会由应用自动联网下载。

导入阶段会先写入同目录临时文件，校验通过才替换正式文件。请至少预留 4 GB 可用空间；如果已有旧模型且准备重新导入，建议预留更多空间。ADB 方式属于开发备用流程，不经过应用内哈希校验，必须自行核对 SHA-256。

### 运行时配置

- Android Gradle 依赖固定为 `litertlm-android:0.18.0`；无需用户填写 API Key、服务地址或云端账号。
- 原生代码先尝试 GPU 文本/视觉后端，音频后端使用 CPU；GPU 引擎初始化失败时回退 CPU。
- 首次加载前，原生层对应用私有目录中的模型文件流式校验 SHA-256；导入流程已经校验过的同一文件修订会在当前进程内按文件长度与修改时间缓存验证结果，避免每次重载重复读取 3.66 GB。
- 如果 GPU 初始化成功但首轮推理明确报出 OpenCL 库不可用，应用关闭旧会话和引擎后重建 CPU 会话，首轮只重试一次；其他错误不自动重放。
- 模型文件、对话上下文和推理均保留在设备本地。下载模型时需要联网，但导入完成后的问答不依赖模型服务器。
- 当前项目没有实现应用内模型下载器。请不要把“模型下载直链”理解成 App 会在后台自动下载。

官方运行文档：[Google AI Edge - Gemma 4 / LiteRT-LM](https://developers.google.com/edge/litert-lm/models/gemma-4)。Google 的公开性能数据来自其标注设备（例如 Galaxy S26 Ultra），不能直接推算 Find N2 的加载耗时或内存；Find N2 的 GPU/CPU 后端、温度和稳定性仍必须实机记录。

## 安装到 OPPO Find N2

先安装本项目生成的 Debug APK，并将模型文件下载到手机可访问的位置（例如“下载”目录）。打开应用「问诊」页，点右上角本地 AI 入口：

1. 点击「选择并导入模型文件」。
2. 在 Android 系统文件选择器中找到 `gemma-4-E4B-it.litertlm`。
3. 等待应用完成本地复制、文件大小和 SHA-256 校验。3.66GB 文件导入期间请保持应用在前台，并确保设备有足够剩余空间。
4. 状态显示文件已安装后，点击「加载本地模型」。

应用只读取用户选择的 URI，不主动请求模型下载服务，也不会上传模型文件；若用户选择云盘类文档提供方，该提供方可能自行联网读取文件。离线验收必须选择设备本地存储中的模型文件。模型不会打包进 APK。导入使用临时文件；校验通过后才替换正式文件。应用启动、查询模型状态或加载模型时会恢复“旧模型已备份、正式文件暂缺”的中断状态，并清理残余临时文件或已完成替换的旧备份。导入失败会保留原模型，或在下一次状态检查时恢复旧模型。

注意：ADB 方式不经过应用内导入流程的校验，但 App 会在首次加载前再次流式计算 SHA-256，匹配后才创建 LiteRT-LM Engine；哈希不匹配时拒绝加载。电脑端手动核对仍建议保留，作为导入前检查。模型加载优先尝试 GPU；GPU Engine.initialize() 失败时会在加载阶段尝试 CPU。若 GPU 初始化成功但首轮推理出现 LiteRT-LM 明确的 `Can not find OpenCL library on this device` 错误，应用会先关闭旧 Conversation 和 Engine，再重建 CPU Engine/Conversation，并只重试该首轮一次。其他运行时错误、CPU 重试失败及已有成功对话轮次后的 GPU 故障不会自动重放。界面显示实际后端，所有回退路径仍需 Find N2 实机验证。

## 当前实现范围

- 完全离线：推理在 Android 本地执行，没有模型 API、远端服务或模型自动下载。
- 文字输入与多轮文字问诊。
- 相机拍摄舌象照片：本地检查文件完整性、文件大小和最低分辨率，再由 E4B 做可见特征描述。
- 最长 30 秒语音录制：WAV、16 kHz、单声道，直接交给 E4B 本地音频输入。 若停止录音失败，界面保留录音可能仍在进行的状态，并允许用户重试停止；未确认结束前不允许发送录音。 录音停止后若文件读取/校验失败，则明确标记录音已停止、拒绝添加附件并提示重新录制。
- 将应用独立记录的用户文字输入和待核对语音识别草稿整理为固定字段；提取使用独立临时会话，不包含舌象图片或模型图像描述；用户核对确认后才返回规则问诊页面。 本地记录每条最多 2000 个 UTF-16 代码单元、最多 100 条、合计最多 16000 个 UTF-16 代码单元；超限时优先保留较新的记录，并在提取提示中明确提示部分早期内容已省略，避免将缺失记录当作用户未提及。 模型返回草稿在 Flutter 层限制为 16000 个 UTF-16 代码单元、单字段 500、列表最多 20 条且每项最多 300；超限直接拒绝进入核对弹窗。已知字段类型不匹配或列表含非文本条目时也直接拒绝，不静默转换为空值。若原始输入记录曾被裁剪，原生层通过 sourceTruncated 明确返回该状态，Flutter 在核对弹窗和确认后的摘要页持续显示提示，不能仅依赖模型自行把缺失内容写入 unknowns。 若记录曾被裁剪且模型未提取出可核对字段，界面会明确提示补充遗漏描述，不使用通用空结果提示掩盖记录缺失。
- 模型加载、会话重置、释放模型内存。会话重置若无法安全关闭旧会话或创建新会话，会尽力关闭引擎并清空运行态；页面同步读取状态，模型需重新加载，不保留半初始化引擎。
- 初始化和推理都运行在单线程后台执行器，不阻塞 Flutter UI。
- GPU 初始化失败时会在模型加载阶段回退 CPU；若 GPU 初始化成功但首轮推理命中明确的 `Can not find OpenCL library on this device` 错误，会关闭 GPU 会话/引擎、重建 CPU 会话并仅重试该首轮一次。其他推理错误、CPU 重试失败以及已有成功对话轮次后的 GPU 故障均不会自动重放。
- 模型提示词限制其职责为健康信息澄清与自述整理，不允许六经辨证、开方或修改剂量。
- AI 对话和结构化草稿不写入 DiagnosticEngine，不自动映射问诊选项，不改变既有规则辨证结果。

## 附件输入边界

音频和图片附件统一执行以下原生输入约束：

- 文件必须位于应用缓存目录内；原生层先解析 canonical path，再校验缓存目录边界，拒绝目录穿越和相邻目录前缀伪装。
- 输入必须是普通文件且非空。
- 文件大小上限为 15 × 1024 × 1024 bytes（15 MiB）；恰好达到上限允许，超过上限拒绝。
- 音频仍限制为最长 30 秒、WAV、16 kHz、单声道。
- 图片在 Flutter 选取/恢复阶段解码检查，短边至少 480 px；相机输出最大边限制为 1600 px。原生入口再次使用 `BitmapFactory` 的 bounds-only 模式检查实际文件尺寸，拒绝无法识别、短边不足 480 px 或长边超过 1600 px 的图像；该检查不完整解码位图，避免在原生校验阶段额外分配整幅图像内存。

相机选图与 Android Activity 丢失结果恢复共用附件操作互斥状态：恢复未完成或相机选图/照片校验进行中，文本编辑与发送、录音、症状整理、会话重置、模型释放及附件移除均停用，避免丢失照片恢复覆盖录音状态，或在会话/模型生命周期切换期间迟到的照片被带入新会话。选图适配器可注入测试；Widget 回归通过挂起恢复和相机选择 Future，验证操作锁定、重复选图被阻止、取消选择后原有文本仍保留。

会话重置、模型释放、模型加载和模型导入共用同一个模型控制互斥锁；操作开始后立即禁用其它模型控制、文本发送、录音、拍照、症状整理和附件操作，直到原生调用及必要状态回读完成。这样可阻止双击导致同类原生操作重复入队，也可阻止推理请求排在模型释放之后执行，或模型加载与导入同时进行。Widget 回归使用可控 Completer，分别验证重置/释放互斥、加载/导入互斥、重复调用被忽略以及忙碌期间输入动作不可用；同时验证照片恢复未完成时模型加载/导入按钮停用，以及加载或导入失败后互斥锁能够释放并允许重试。

CI 的 Kotlin 单元测试覆盖缓存目录内嵌套文件、恰好达到 15 MiB、超过上限、缓存目录外路径/相邻前缀目录，以及目录/缺失文件/空文件拒绝；图片策略测试覆盖 480 px 与 1600 px 边界、越界尺寸和无法解码尺寸。自动化测试验证的是路径和输入边界，不替代设备文件系统、录音和拍照链路的实机验收。 WAV 策略测试还覆盖 RIFF 主体截断、奇数长度扩展 chunk 的 padding、重复 `fmt ` / `data` chunk、无音频数据、错误编码参数和 30 秒边界。Flutter 界面回归测试覆盖对话重置与模型释放后的状态切换。 同时覆盖重置失败、释放失败时保留当前会话/模型状态并显示错误。 录音回归测试覆盖停止失败后恢复停止入口、重试成功后再进入附件待发送状态。 原生输入记录策略测试覆盖单条/总量/条数上限、截断标记和 Unicode 代理对边界。 模型导入恢复测试覆盖备份恢复、正式文件替换完成后的残余文件清理和未完成临时文件清理。 重置/释放失败后若原生状态已变为 not_loaded，Flutter 会同步清空失效历史和附件，避免重新加载后把旧消息误认为当前会话；若原生仍报告 ready，则保留原对话。 若状态回读本身失败，界面进入状态未知隔离态，停用问诊、模型加载和文件导入；用户显式重查后，若确认 not_loaded，再清理旧会话和附件。 推理结束后的状态回读失败也进入同一隔离态：已生成的回复保留，失败输入保留在编辑框；重新确认模型状态前不允许继续发送。 若状态回读成功但明确返回 not_loaded，则清除旧会话历史：推理成功时仅保留本轮已生成回复并标注会话已结束；推理失败时保留编辑框文本及附件，清除旧聊天气泡，加载模型后可重新发送。

## 尚未接入

语音播报、经实机校准的清晰度/模糊度检测，以及已确认症状到规则问诊选项的显式映射仍未接入。当前照片检查只覆盖文件、分辨率和尺寸，不代表已完成完整的舌象图像质量评估。后续必须逐项实现并测试，不能将模型原始回复直接作为辨证输入。

## Find N2 实机验收步骤与通过条件

必须使用 OPPO Find N2（PGU110，16 GB）进行以下验收；CI APK 编译通过不能替代本节。

### 0. 内外屏全屏适配

Find N2 外屏和内屏必须分别测试，不能只在外屏完成 AI 模型验收：

- 外屏约 403 dp 窗口宽度：应显示底部导航，页面单列、输入框和主要按钮不被手势区遮挡。
- 展开内屏约 775 dp 窗口宽度：应显示左侧 NavigationRail；检查知识、工具、问诊、收藏四个主入口的内容列宽和滚动。
- 折叠/展开过程中确认当前 Tab、滚动位置、问诊文本草稿没有被清空或重置。
- 字号测试覆盖 100%、150%、200%；键盘弹出、相机、文件选择器和模型导入分别在内外屏操作。
- 记录运行时实际 dp 宽高和 `MediaQuery.displayFeatures`。窗口模拟测试只能证明布局断点，折痕/半折叠和系统窗口行为必须真机验收。
- **PASS**：关键页面全屏占用当前应用窗口，无横向溢出、关键控件跨越遮挡铰链、输入区不可见或内容被裁剪。
- **FAIL**：仅内屏出现黑边/ letterbox、布局仍使用外屏比例、键盘挡住输入区或折叠切换丢失当前操作。
- **MISSING**：没有在 Find N2 真机执行并留存截图与窗口尺寸。

### 1. 安装与离线条件

- 安装本轮 CI 生成的 Debug APK，确认 Android 包名为 `com.nihaisha.nihaisha_app`。
- 将模型复制到应用私有目录，核对文件大小为 `3,659,530,240` bytes，SHA-256 与上文一致。
- 开启飞行模式，并确认 Wi-Fi、移动数据均关闭后再启动应用。
- **PASS**：模型文件状态正确；离线状态下可加载模型、连续发送文字并收到回复；抓取日志没有模型网络请求。
- **FAIL**：要求联网、下载模型、文件校验不通过却仍开始推理，或应用崩溃。

### 2. 文字问答

- 冷启动后首次加载模型，记录加载耗时、实际后端和峰值内存。
- 连续完成至少 10 轮不同问题；中间穿插重置会话，再完成 3 轮。
- **PASS**：每轮均返回非空文本；重置后不复用旧会话上下文；前台 UI 可响应；无进程被系统杀死。若首轮 GPU 推理出现明确 OpenCL 库缺失错误，界面最终显示 CPU，首轮只重试一次并成功；若没有触发该错误，记录实际后端即可。
- **FAIL**：会话串线、空回复、主线程长时间阻塞、崩溃或系统杀进程。

### 3. 音频输入

- 录制 5 秒普通话、15 秒连续描述、25 秒带停顿描述各一段。
- 录音文件应为 WAV、16 kHz、单声道；最长录音不能超过 30 秒。音频文件进入原生推理前还必须通过应用缓存目录、普通非空文件及 15 MiB 大小上限校验。
- **PASS**：离线模型返回与录音相符的逐句转写；听不清处明确标记，不补写症状；用户可移除附件并重新录音。
- **FAIL**：静默丢失录音、附件被覆盖、越过 30 秒或 15 MiB 限制，或模型把不确定语句改写成确定症状。

### 4. 舌象照片输入

- 分别拍摄正常光线、偏暗、反光、轻微失焦四种照片；每次发送前检查预览。
- 图片文件进入原生推理前必须通过应用缓存目录、普通非空文件及 15 MiB 大小上限校验；短边至少 480 px，处理尺寸最大边不超过 1600 px。
- **PASS**：模型只描述可见颜色、舌体形态和舌苔；不输出六经辨证、疾病诊断、方剂、药物或剂量；失败图片可以移除并重拍。
- **FAIL**：把照片观察自动写进用户自述草稿，或模型直接作辨证/处方结论。
- 注意：当前客户端没有经实机校准的模糊度、曝光或色温阈值；这组测试只验输入链路和输出边界，不代表图像质量检测已经完成。

### 5. 资源与稳定性

- 连续执行 10 轮文字问答、3 段音频、5 张图片；随后释放模型，再次加载。
- **PASS**：记录加载、首轮回复和各任务耗时；释放后可再次加载；无持续增长导致的 OOM 或系统杀进程。
- **FAIL**：释放期间仍有推理任务、资源无法重新初始化、持续 OOM 或严重热降频导致任务无法完成。

### 6. 记录模板

在开始实机测试前，先从仓库根目录运行 `./tool/capture_find_n2_metrics.ps1`。脚本仅保存 `[WINDOW_METRICS]` 行，设备信息单独写入同一采集目录的 `device-metadata.json`；不会把其他 Flutter 日志或问诊内容写入记录。采集期间依次操作外屏、内屏、半折叠、键盘、相机和文件选择器，结束后将日志、系统截图与本节记录模板放在同一验收批次中。

每次测试填写：APK commit SHA、APK 文件 SHA-256、设备型号/系统版本、模型 SHA-256、飞行模式状态、加载耗时、后端、失败阶段（Engine 初始化/Conversation 创建/文字/音频/图像推理）、首轮/多轮耗时、任务结果、峰值内存、温度/降频现象、失败日志。未测试项目标记 `MISSING`，不得写成 PASS。

## CI Debug APK 架构
GitHub Actions 的 Find N2 验证构建固定生成一个普通的 `arm64-v8a` APK：命令为 `flutter build apk --debug --no-pub --target-platform android-arm64 -P disable-abi-filtering=true`，工件路径为 `build/app/outputs/flutter-apk/app-debug.apk`。`--target-platform` 限定 Flutter 引擎目标架构，`-P disable-abi-filtering=true` 关闭 Flutter Gradle 插件默认注入的多 ABI NDK 过滤器；CI 的 Gradle `defaultConfig.ndk.abiFilters` 只保留 `arm64-v8a`，并禁用 ABI splits，避免 Flutter CLI 将 split APK 误判为缺少预期的 `app-debug.apk`。该限制只由 CI 环境属性 `ciArm64Only=true` 启用；本地构建和正式发行仍按 Gradle 默认配置生成 `armeabi-v7a`、`arm64-v8a`、`x86_64` 分包及通用 APK。
