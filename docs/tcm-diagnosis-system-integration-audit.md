# Wsy-prog/tcm-diagnosis-system 对照审计

> 审计对象：`Wsy-prog/tcm-diagnosis-system` 默认分支 `index.html` 与 `just2512/nihaixia-app` 默认分支辨证引擎代码。
> 本文是代码结构与规则实现审计，不构成医学有效性验证，也不代表已经完成全部数据逐条比对。

## 结论

**不整体移植，不替换现有辨证引擎。** App 已经实现了上游项目的主要辨证能力，而且在规则表达、输入门禁和测试可维护性上采用了不同实现。当前可确认的增量主要是“脏腑维度信号的可解释呈现”，但上游的 `zangfuScore` 只是从问诊选项累加出来的信号容器，不能直接视为独立脏腑辨证算法。

本轮不修改诊断结果、规则门禁、方剂推荐或处方生成。先冻结移植范围，后续只对有明确差异且可测试的展示/证据层做增量。

## 一、App 已有能力（重复建设，暂不移植）

核查文件：

- `lib/engine/diagnostic_engine.dart`
- `lib/engine/diagnostic_rules.dart`
- `lib/engine/rule_engine.dart`
- `lib/engine/formula_rules.dart`

已确认：

1. **六经问诊与方证规则**：App 使用 Q1–Q12 结构化答案和扩展症状；`FormulaRule` 将 `required`（必选门禁）、`reference`（参考信号）、`extRequired`、`extReference` 分开。
2. **硬门禁**：`RuleEngine.evaluate()` 要求所有必选项满足，否则候选被排除；参考项只参与候选排序。不能用上游软匹配替换该门禁。
3. **合病并病**：`DiagnosticRules.combinedPatterns` 当前定义 20 个 `CombinedPattern`；`DiagnosticEngine._detectCombinedPattern()` 使用分经条件信号，并将命中的 condition key 精确映射到规则表，不是直接按两个经分值接近来认定合病。
4. **脉舌矛盾**：已有 `pulseTongueContradictions` 规则表；`_detectPulseTongueContradiction()` 还有显式矛盾分支，并将矛盾作为诊断结果的警示字段返回。
5. **脉象组合、真寒假热、传经、鉴别诊断、汗法禁忌、用药规则**：均已有对应的数据结构或检测逻辑。
6. **经典依据**：合病规则含条文出处字段；鉴别规则含经典文本和辨点字段。

因此，上游的六经公式、合病表、脉舌矛盾提示和感冒关键词匹配，不应作为新功能直接复制进 App。

## 二、上游实现审计

上游 `index.html` 中可确认的实现：

### 1. 六经与脏腑信号

`collectSignals()` 同时建立 `meridianScore` 与 `zangfuScore`，将非六经标签累加到 `zangfuScore`。当前检索到的代码显示这是问诊选项的权重汇总；未发现与 App 的 `FormulaRule` 等价的脏腑必选条件、独立脏腑证型裁决链或完整的反证处理。

**审计结论：** 可以借鉴“双维度并列展示”的数据组织思路；不能把 `zangfuScore` 直接接成脏腑诊断，更不能将其与六经分值合并成一个总分。

### 2. 六经公式匹配

`matchFormulas()` 将已选症状标签拼接后，以 `includes()` 对照公式条件；脉象另转成“脉+脉名”再做前缀匹配。

**风险：** 这种字面包含逻辑没有充分表达否定、症状时间、严重程度、同义词边界和互斥选项。App 已有结构化选项编号与规则字段，不能退回到拼接字符串匹配。

### 3. 合病判断

`matchHebing()` 取六经分值前两位，在第二位达到第一位 70% 时查合病表。

**风险：** 比值阈值只是相对分值接近，不代表两经各自满足对应条文或方证的必要条件；还可能受问项数量、权重配置和缺失回答影响。App 当前的精确条件 key 机制应保留。后续若审计发现某条 App 规则缺少经典条件，应补具体条件与测试，而不是引入 70% 阈值。

### 4. 脉舌交叉验证

`matchPulseTongue()` 查脉象表、舌象表和预设矛盾组合，返回冲突记录；未见它根据冲突自动覆盖主证或方剂。

**审计结论：** 其“独立返回冲突信息”的分层方式可作为展示层参考。App 已有相同能力，不需要复制上游表；应重点核查 App 规则覆盖、输入组合和提示是否被 UI 完整呈现。

### 5. 四联征与附子提示

`matchSiniTrio()` 仅按失眠/睡眠、便秘/硬结、冷/冰、无汗四类字符串中命中至少三类触发提示，并在提示文本中给出血癌、狼疮、糖尿病及生附子剂量相关表述。

**REJECT：** 不得移植到 App 的自动辨证、方剂推荐、剂量生成或用药提示链。它没有展示疾病特异性证据、排除条件、剂量安全校验或临床验证；仅凭四类宽泛字符串命中就关联重症和生附子剂量，存在严重误导和用药风险。若作为历史资料展示，也必须脱离患者诊断流程并重新核验来源、上下文和安全性。

## 三、差异处理清单

| 项目 | 处理 | 原因 |
|---|---|---|
| 六经问诊、六经公式 | 不移植 | App 已有结构化 Q 选项与必选门禁 |
| 合病并病 | 不移植上游算法 | App 已有 20 条精确条件规则；拒绝 70% 相对分值阈值 |
| 脉舌冲突 | 不复制规则表 | App 已有冲突规则和结果警示字段 |
| 脏腑维度 | 有条件补充展示层 | 上游只有权重聚合信号，尚不足以构成独立辨证 |
| 经典/方证/医案关联 | 做数据完整性审计后再决定 | App 已有经典条文与方剂联动，需查具体缺项而非重复导入 |
| 感冒速配 | 不直接移植 | 上游按症状字符串计分，需逐条核验方证必要条件与禁忌 |
| 四联征/生附子提示 | REJECT | 条件宽泛且包含高风险剂量提示，不进入自动流程 |

## 四、下一步实施边界

后续只允许按以下顺序推进：

1. **数据差异审计**：将上游六经/脏腑标签、脉舌冲突组合、合病条目逐条映射到 App 已有规则，输出新增、重复、冲突、来源不清四类记录。
2. **脏腑展示方案**：若数据字段足够且来源明确，新增独立的“脏腑相关信号”区域，只展示命中项、来源问答、支持/反向证据和缺失信息；不输出脏腑确诊，不覆盖六经结果。
3. **测试先行**：新增规则必须包含正向、反向、缺失答案、矛盾输入、否定表达和边界条件测试；任何规则变化都不得放宽必选条件门禁。
4. **回归验证**：运行相关 Dart 测试、`flutter analyze` 和完整 `flutter test`；如涉及 UI，再补 Android/Find N2 内外屏验证。
5. **许可核对**：上游仓库的 `LICENSE` 为 MIT，App 为 Apache-2.0。两种许可证可兼容，但若复制上游代码，必须保留 MIT 版权与许可声明；数据、经典注释和外部素材的授权需单独核查，不能仅凭仓库 LICENSE 推定全部数据可自由复制。
